# What I learned benchmarking 9 local coding models on a 48 GB Mac

I wanted to know whether a local model could act as the *worker* in a hybrid setup —
a big cloud model plans and reviews, a local model does the bounded editing. So I
built a harness that grades models objectively and ran nine configurations through it.

The model rankings turned out to be the least interesting part. The useful findings
were the things that silently broke before any model quality mattered at all.

**Read this first:** the benchmark is **two tasks on one repository, single-shot,
single-turn, no tool use**. That is a narrow basis. Decoding is greedy, so results
are *reproducible* — one model reproduced its scores token-for-token across three
separate runs — but reproducible is not the same as representative. Treat the
harness as the contribution and the numbers as a starting point.

---

## The setup

- Apple M5 Pro, 48 GB unified memory (~36 GB usable for GPU work)
- `mlx_lm.server` 0.31.3, one model resident at a time
- Fixture: a React + TypeScript weather app **generated by a local model**, which
  shipped with two real build errors

Grading is mechanical. The model proposes an edit → we apply it to an isolated copy
→ run `tsc`. A run passes only if the target error is gone **and** no new error
appeared. No human judgement.

The two tasks:

| Task | Error | Correct fix |
|---|---|---|
| **T1** | `TS6133: 'error' is declared but its value is never read` (App.tsx:149) | `.catch(error =>` → `.catch(() =>` |
| **T2** | `TS2503: Cannot find namespace 'NodeJS'` (SearchBar.tsx:30) | `NodeJS.Timeout` → `ReturnType<typeof setTimeout>` |

T1 looks trivial. It is not: `error` is declared **twice** in that file — once as a
`useState` variable, once as the `.catch()` parameter. The compiler points at line
149. Resolving which `error` it means is the whole task.

Each model ran both tasks under two strategies: return the **whole corrected file**,
or return a single anchor-based **SEARCH/REPLACE** block.

## 1. The winning behaviour: refusing to trust a line number

T1 defeated eight of nine configurations. The failures were nearly identical — the
model would confidently rewrite the file and change *nothing*, or edit the wrong
`error`.

Asking one to reason out loud showed why:

> "The error refers to line 149, which is `const error = localStorage.getItem('error');`"

**That line does not exist anywhere in the file.** With the complete file in its
context, the model *fabricated* the source line, then reasoned flawlessly from an
invented premise.

Now compare gpt-oss-20b, which got T1 right:

> "In App.tsx line 149,16. **Let's count lines? But easier: In handleCitySelect, we
> have ca[tch]**..."

It explicitly declines to count to line 149 and finds the code **semantically, by
enclosing function**. That is the entire difference.

**Practical takeaway:** don't hand a local model `error X at line N`. Hand it the
enclosing function name and the verbatim snippet. Line numbers invite fabrication.

---

## 2. Chain-of-thought made the coder model *worse*

Qwen3-Coder has no thinking mode, so I induced reasoning by prompt — including an
explicit warning about shadowed identifiers.

| | Plain | With CoT |
|---|---|---|
| Score | **2/4** | **0/4** |

It broke both tasks it previously got right. Reasoning over a fabricated premise
produces a *confident, well-argued* wrong answer. CoT laundered the hallucination
instead of catching it.

For the model that *does* have a thinking mode (Qwen3.5-35B), enabling it helped:
1/4 → 2/4. So reasoning is not universally good or bad — it helped the model
trained for it and hurt the one that wasn't.

---

## 3. Higher precision changed nothing

Running the same model at 5-bit and 6-bit produced **byte-identical output** on T1 —
same 1,604 tokens, same failure, both strategies.

The hallucination is not a quantization artifact. 6-bit cost 7 GiB more resident
memory for exactly zero improvement.

---

## 4. `sliding_window` is the wrong thing to screen on

A widely repeated rule says a model with a small sliding-attention window can't hold
long context and is unusable for multi-turn work.

**gpt-oss-20b has `sliding_window: 128`** — and it retrieved a canary token planted
20,000 tokens earlier without difficulty. Because it *interleaves*: 12 of its 24
layers are full attention.

Screening on `sliding_window` alone would have rejected the second-best model here,
and would also reject Gemma and Mistral variants.

**Screen on `layer_types` instead** — do *any* layers do full attention, and how
many. [`harness/screen_config.py`](harness/screen_config.py) does this in one HTTP
request, before downloading 20 GB:

```
mlx-community/gpt-oss-20b-MXFP4-Q8
  model_type          gpt_oss  (supported)
  sliding_window      128
  full-attn layers    12 of 24
  KV per token        24.0 KiB
  -> OK
```

## 5. MoE vs dense decided everything about speed

| | Qwen3.6-35B-A3B (MoE) | Qwen3.6-27B (dense) |
|---|---|---|
| Score | 4/4 | 4/4 |
| Total time | **152s** | 783s |
| KV per token | **20 KiB** | 64 KiB |

Identical scores. **5.2× faster.** Generation rate tracks *active* parameters, not
total: ~65 tok/s for 3B-active MoE models, ~12–18 tok/s for dense 24–36B ones. Every
slow model in the table is dense.

---

## 6. SWE-bench rank did not predict single-shot editing

Devstral-Small-2-24B is #1 open-source on SWE-bench and purpose-built for agentic
code editing. It came **last, 1/4**, changing 74 and 113 lines on one-line fixes.

It could produce well-formed anchor edits — it never paraphrased the source, unlike
some others — it just made the wrong edit. SWE-bench measures multi-turn agentic work
*with test feedback in the loop*. That is a different skill from one-shot bounded
editing, and the ranking doesn't transfer.

---

## 7. Diff-only editing is cheaper for identical correctness

Same model, same task, only the strategy varied:

| Strategy | Result | Tokens | Time |
|---|---|---|---|
| Whole file | pass | 701 | 10.9s |
| SEARCH/REPLACE | pass | 227 | 3.5s |

**3.1× fewer tokens, 3.1× faster, same fix.** Whole-file rewriting also invites
scope creep — the biggest over-reaches in the whole run (243, 113, 74 lines changed
for one-line fixes) were all whole-file.

One caveat: anchor edits require the model to reproduce source text *verbatim*. One
model silently dropped a `try {` line from its SEARCH block, so the edit never
applied. That's a real failure mode worth detecting explicitly.

## Two things that broke before any model ran

**MLX aborts if it finds the wrong MPI.** `mlx_lm.server` `dlopen()`s
`libmpi.dylib`. If that resolves to Anaconda's MPICH instead of Open MPI, it
`SIGABRT`s before loading any weights:

```
[mpi] MPI found but it does not appear to be Open MPI. MLX requires Open MPI but this is MPICH
```

`DYLD_LIBRARY_PATH` does **not** fix this — I verified the variable reaches the
process. Reordering `PATH` doesn't either. The knob that works:

```bash
MLX_MPI_LIBNAME=/opt/homebrew/opt/open-mpi/lib/libmpi.dylib mlx_lm.server --model ...
```

**Prefill is the memory event, not KV growth.** A 74K-token prompt drove a 48 GB
machine to within 4 GB of full — twice — while the server's resident memory sat flat
at 18.6 GiB. The spike is prefill activation buffers, not accumulated KV cache.

Lowering `--prefill-step-size` from the default 2048 to 512 made it *both* safer and
faster:

| prefill step | available memory during prefill | throughput |
|---|---|---|
| 2048 | oscillating 6–10 GiB | ~410 tok/s |
| 512 | stable ~14.7 GiB | ~750 tok/s |

If you're modelling memory as `weights + kv_per_token × context`, you're missing the
term that actually binds.

## Two reporting traps

**"Cache write: 0" doesn't mean caching is broken.** Every session I looked at showed
`cache write: 0` alongside 60–100K cache reads. MLX emits
`prompt_tokens_details.cached_tokens` — a cache-*read* field — and **no cache-write
field at all**, so the client had nothing to display. Caching works fine: replaying
an identical prefix went **8.8s → 0.2s, a 44× speedup**.

**Thinking models can return no `content` field at all.** One model returned
`['role', 'reasoning']` — 42,958 characters of reasoning, `content` absent entirely.
A client reading `message.content` gets nothing and appears to hang. If you're
integrating a thinking model, read `reasoning_content` too, and budget enough tokens
for it to finish reasoning *and* answer.

## What I'd actually deploy

**`mlx-community/Qwen3.6-35B-A3B-4bit`** — 4/4, 152s, cheapest KV of anything tested
(20 KiB/token).

**`mlx-community/gpt-oss-20b-MXFP4-Q8`** if headroom matters — 3/4, but its only
failure is whole-file, which the diff-only rule forbids anyway. Under that strategy
it's effectively 2/2, at 11.7 GiB and 67s. Apache 2.0.

```bash
MLX_MPI_LIBNAME=$(brew --prefix open-mpi)/lib/libmpi.dylib \
mlx_lm.server --model mlx-community/Qwen3.6-35B-A3B-4bit \
  --host 127.0.0.1 --port 8085 --prefill-step-size 512
```

## Limitations

Two tasks, one repository, one attempt each, single-turn, no tool use. Greedy
decoding makes it deterministic, not general. The 4/4-vs-3/4 ordering between the
top two models is **not** something I'd defend on this evidence — that they both beat
the older models is much better supported. Timings are one machine, one run.

I have not tested multi-turn agentic loops, which is where these models are actually
used, and where I'd expect the ranking to shift.
